# Officer Review Verification Payload Fix

## Symptom
Officer task existed but review screen displayed:
"No verification payload available."

## Root Cause
The officer review page was relying exclusively on the Application Service's `verificationData` replica, which might not be populated or available at the time of review. The actual canonical verification result is generated securely within the BPMN workflow in `VerifyDataWorker` and is available natively inside the Camunda Task context as the `verificationResult` process variable.

## Data Flow Before
Interoperability Service -> VerifyDataWorker -> Workflow Status Worker -> Application Service -> Frontend 
This path was fragile because callback failures to Application Service (or eventual consistency delays) meant the frontend couldn't fetch the JSON payload, despite the workflow having already securely verified and transitioned the application to the Officer Review state.

## Data Flow After
Interoperability Service -> VerifyDataWorker -> Officer Task (Camunda variable) -> Frontend
The officer frontend now relies primarily on the authoritative `verificationData` exposed directly by the Security Workflow Service's `/api/v1/officer/reviews/{taskId}` endpoint, with the Application Service acting only as a fallback.

  Added the optional `verificationData` attribute to match the updated contract.
- **`frontend/src/pages/officer/ReviewTaskPage.tsx`**:

- **`frontend/src/__tests__/officer.test.tsx`**:
  Added new regression tests and fixed existing string assertions.

## Security
No raw interoperability payloads, tokens, or unauthorized data is exposed. We are strictly re-using the **safe**, canonical `verificationResult` JSON generated by the `VerificationService` (which has already removed raw data). Department authorization is fully intact.
